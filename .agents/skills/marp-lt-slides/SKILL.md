# Marp LTスライド

発表資料を、次の2つの情報経路に分けて設計する。

- 聞き手が見るもの：主張、関係、対比、根拠
- 発表者が話すもの：背景、解釈、注意点、次へのつなぎ

画面に見えている文章をカンペで繰り返さない。見れば分かる内容については、なぜ重要なのか、何に注目してほしいのか、次のスライドへどうつながるのかをカンペに書く。

## 現在のプロジェクトを確認する

編集前に次を行う。

1. リポジトリの指示と、対象スライドの最新版を読む。
2. 参考にできる既存スライドと、使用中のMarpテーマを確認する。
3. 発表内容の根拠と実装上の限界が書かれた資料を読む。
4. ユーザーによる編集を残す。並行して編集される可能性があるため、反復修正の直前に対象箇所を読み直す。

既存LTのディレクトリへ別の資料を追加するときは、元の資料を上書きしない。ユーザーが置き換えるファイルを明示しない限り、別のMarkdownファイルとして作る。

## 詳細より先に話の流れを作る

初期案では、タイトルと各スライド1〜2行程度の概要だけで、すぐにMarp生成できるMarkdownを作る。LTの流れとして、次の形が使いやすい。

1. 聞き手が共感できる具体的な困りごと
2. 困りごとの裏で人間が担っていた役割や仕組み
3. 見方を変えるきっかけになった着想や既存事例
4. 実際に作ったもの、試したこと
5. 中心となる仕組み
6. できるようになったことと、まだ粗いところ
7. 持ち帰ってほしい問いや考え方

発表者の体験に合わせて変更し、固定のスライド数を押しつけない。内容を詰める前に詳細を創作しない。

目次は制作途中では仮置きにする。HTMLコメントで「内容確定後に整理する」というTODOを残し、流れが固まった後で更新する。すべてのスライド名を並べるのではなく、物語の大きな区切りを短く示す。

## 画面とカンペを分離する

カンペは、見出し直後のHTMLコメントへ書く。

```markdown
## スライドの主張

<!--
  - 画面には出していない背景を話す
  - 図がなぜ重要なのかを説明する
  - 誤解を避けるための限界を補足する
  - 次のスライドへつなぐ
-->
```

画面に置くもの：

- 短い主張や印象に残る問い
- 対比、対応関係、順序、状態遷移、構成図
- 根拠として機能する小さなコードや設定例
- 聞き手が話を追うために必要なラベル

カンペに置くもの：

- 動機や時系列の背景
- 画面にある図の解釈
- 主張できる範囲と避けるべき誤解
- 画面には長すぎる具体例
- 次のスライドへのつなぎ

箇条書きをそのまま読み上げるカンペは避ける。図や対比で分かる内容を、長い文章として画面に置かない。

## 関係に合った見せ方を選ぶ

単純なMarkdownやASCII図では中心的なアイデアが素朴に見える場合、スライド内のHTMLレイアウトを使う。

- 責務分離やBefore/After：左右2カラム
- 処理順序：横並びのカードと矢印
- 2つの着想の合流：2枚のカードから1つの結論へ合流
- オーケストレーター：中央のカードを強調
- Phase、Human Gate、Rollback、操作：意味ごとに色と形を統一
- 暗黙状態から明示状態への変換：会話と構造化データのBefore/After

色の意味は資料内で統一する。スライド固有の配置にはインラインスタイルを使い、複数スライドに共通する規則だけをテーマCSSへ追加する。

すべてのスライドを装飾しない。関係を短時間で理解しやすくなる場合にだけ図解する。気づきやまとめのスライドは比較的静かな見た目にする。

ローカル画像にはMarp記法でサイズを指定するか、幅を制限したカラム内へ置く。

```markdown
![図 width:100%](diagram.png)
```

画像と説明が競合するときは、文字と画像を左右に分ける。両方を無理に縮小しない。

## AIワークフローの発表では状態の外出しを見せる

AIワークフロー、オーケストレーション、ループエンジニアリングが主題なら、一般的な状態機械の図だけで終わらせない。実装の中心にある場合は、次の変換を示す。

```text
人間とAIの会話                 manifest / result
暗黙的な状態          ->       機械可読な状態
```

現在Phase、Rollback先、Retry回数、Gate状態などを、小さく現実的な設定例で見せる。重要なのは永続化だけではない。明示された状態と遷移ルールをEngineが読み、次へ進む、再試行する、戻る、人間を待つ、停止する、という判断へ使えることをカンペで説明する。

責務を明確に分ける。

- AI：現在のPhaseを実行し、結果を返す。
- Engine：完了条件を検証し、状態遷移を適用する。
- 人間：明示された判断境界で操作する。

セキュリティ境界、完成度、汎用性、標準への準拠、着想元との実装上の同一性を誇張しない。発表の意味を左右する粗さや制約は示す。

## 発表者の編集を壊さず反復する

小さな見た目の修正では、指定されたスライドだけを変更する。他の箇所にある表現や手動変更を維持する。ファイル全体の整形より、対象を限定したパッチを優先する。

「いい感じに飾る」と依頼されたら、次の順で考える。

1. そのスライドが示したい関係を特定する。
2. ASCII図や平坦な箇条書きを、最小限の適切な図へ置き換える。
3. 会場で読める短いラベルにする。
4. 文字サイズやカード幅は、指定されたスライド内だけで調整する。
5. 変更のたびにMarpで生成確認する。

カードの幅、文字サイズ、画像配置の変更依頼から、他スライドの変更まで許可されたと推測しない。

## Marpで検証する

リポジトリに記載されたビルドコマンドを使う。固有のコマンドがない場合は、テーマとローカル画像の利用を指定して生成する。

```bash
marp path/to/slide.md \
  --html \
  --theme-set ./themes/theme.css \
  --allow-local-files \
  -o /tmp/slide-preview.html
```

ユーザーがHTMLやPDFの生成を求めていない限り、確認用出力は一時領域へ置く。次を確認する。

- Marp変換が成功する。
- スライドの見出しと順序が意図どおりである。
- ローカル画像のパスが解決できる。
- 横方向に密なレイアウトがテーマの本文幅に収まる。
- カンペがHTMLコメント内にあり、画面へ表示されない。

変更したソースファイルと検証結果を報告する。コンパイル成功だけでは、密なレイアウトが視覚的に収まる保証にはならない。厳密な収まりが重要なら、レンダリング結果も確認する。
